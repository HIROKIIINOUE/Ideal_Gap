# 長期目標機能を廃止、ダッシュボードからタスクタイマーへ直接アクセス可能へ

## 背景-1 アプリ操作の複雑度の解消

ユーザがアプリのメイン機能であるタスクタイマーとタスク音楽への再生へ辿り着くまでの操作が複雑で工程が多すぎる。
テスターより操作が複雑だという声が届いた。
また、タスクタイマーとタスク音楽が本アプリの強みなのでそこに辿り着けないユーザがいた。

## 背景-2 理想の自分と長期目標の重複性

テスターより「理想の自分ページと長期目標ページの違いがわからない」という声が届く。
また、操作が多すぎてすぐに理解できない、複雑すぎるという声が届く

## 新要件

### 長期目標ページの廃止

長期目標管理機能を廃止する。
ダッシュボードより長期目標ページカードを削除する。
現在のDBにある以下の長期目標テーブルは当面残すが、長期的には削除を予定している。
月間目標を削除した時と同様に長期目標のコードベースもリポジトリに残すが(今後もし機能を復元するときに参考にできるため)、
本アプリの各機能とは完全に切り離し全ての機能、UI/UXに影響が出ないようにする(一部切り離しが難しいor複雑化する時は削除しても良い)
一方でユーザテーブルのcurrent_point varcharは完全に廃止しDBからも削除する。
長期目標以外でcurrent_pointを使用している箇所があればその記載は全て削除。

```
Table long_term_goals {
  id uuid [pk]
  user_id uuid [not null, ref: > users.id]
  until_when varchar [not null]
  description varchar [not null]
  is_done boolean
  "order" int // ソート用
  created_at timestamptz
  updated_at timestamptz
  Indexes {
    (user_id, "order")
  }
}
```

### ダッシュボードにタスクタイマー追加

ダッシュボードにタスクタイマーカードを設置。
カードの順番は左上から「理想の自分」「年間目標」「週間タスク」「タスクタイマー」「タスク集中音楽」「休憩通知」。
タスクタイマーカードを押下するとモーダルが表示されそこで紐づける週間タスクを選択することができる。
ユーザは週間タスクを紐付けない(タイマーだけの利用)をすることもできる。
(週間タスクが０件の場合は選択インプットの上に「週間タスクがまだ設定されていません」という文言を表示し値はデフォルト値の「週間タスクを紐付けない」に設定する)
紐づけられた場合は、週間タスクから遷移する場合と全く同じ仕様でユーザがタスクタイマーを使用できる。
タイマー完了モーダルの保存ボタンで週間タスク(+紐づく年間目標)へ時間が蓄積される。
紐づけられない場合は「完了モーダルから次回のスタート地点入力欄を非表示」「完了モーダル下部のボタンの上に"タイマーが週間タスクに紐づいていないため作業時間は蓄積されません"とメッセージを入れる」「完了モーダルの紐づく場合は"保存"、紐づかない場合は"完了"と文言を変更する(ユーザの混乱を避けるため)」「手動時間記録カードを非表示」を実施。
モーダルUIデザインは週間タスクの追加モーダル画面に寄せる、ドロップダウン式の選択欄で紐づく週間タスクを決める。(デフォルト値は「週間タスクと紐付けない」)
ボタンは「戻る」と「次へ」の２つを設置。戻るボタンの押下するとモーダルが消え、次へを押すとタスクタイマーページへ遷移する。

## LPやダッシュボードの文言変更

今回の機能変更に伴いLPのアプリ説明欄やダッシュボードの各カードの文言に矛盾がないように修正
タスクタイマーカードの文言は以下のようにしてほしい。(フランス語は英語をもとに自然な文章でcodexに作成してほしい)

「日本語」
計画を立てたら次は行動。タスクタイマーでモチベーションを保ち、タスク音楽で集中力を最大化。
「英語」
Keep motivated with Task Timer and stay focused with Task Music
Gardez votre concentration Minuteur de tâche et Musique de travail.

## 疑問点

- 上記のDBを削除しても既存のユーザへ影響は出ないか
- ダッシュボードへタスクタイマー導線を導入することで生じるリスクは何か

## 現状コードへの影響と対策

アカウントの削除処理では既存のユーザのためにlong_term_goals はテーブルが残っている場合のみ削除対象。current_point は参照を全削除
long_term_goals や current_point を参照して Supabase エラーになる箇所の洗い出し
TaskTimerScreen は taskId がない状態だと保存時にエラーになるため、紐づけなしの場合は保存処理ではなく「完了してセッションをクリアしてダッシュボードへ戻る」専用分岐を用意する

## codexがリストアップしたリスクへの対策

- ユーザーが「タイマーを使ったのに年間目標に反映されない」と誤解する → 紐づいた週間タスクがない場合は完了モーダルでメッセージを表示(上述)
- ダッシュボードから開始したのに完了後に週間タスクへ戻ると違和感がある → ダッシュボードからの遷移の場合は完了モーダル処理後に週間タスクリストではなくダッシュボードへ戻るように設定。手動遷移カードは「週間タスクへ」「ダッシュボードへ」の両方があるのでそのままでだ大丈夫
- 週間タスクが0件のユーザーに対するモーダルの空状態が必要 → 週間タスク追加モーダルにおける「年間タスク紐付け」と同じようにドロップダウンの選択肢の最上部を「紐付けしない」としそれをデフォルト値とすることで週間タスクが存在しなくても「紐付けしない」が設定される
- タイマー中に紐づけた週間タスクが削除された場合の保存失敗処理が必要 → 保存時に週間タスクが存在しない場合は、作業時間を蓄積せず、完了モーダル上で「紐づけた週間タスクが削除されたため作業時間は保存されません」と表示する。ボタンは「完了」のみとし、押下でタイマーセッションをクリアしてダッシュボードへ戻る。
- PostHog/Sentryで「紐づけあり」「紐づけなし」を分けないと分析が濁る → ここは一旦放置で、後ほど検討しましょう。
- LP・ダッシュボード・要件定義に長期目標の説明が残ると、ユーザー体験と説明が矛盾する → ここは修正が必要(上述)
