# 要件定義

## 1,プロジェクト概要

### 1-1, プロジェクト名

Ideal Gap

### 1-2, 目的

ユーザーが理想の自分に近づけるための手助けをするアプリ。具体的には以下 4 点。

1,理想の自分可視化機能
→ 理想の自分の姿を知る(現在と理想のギャップを知る)
2,年間目標・月間目標リスト機能
→ 理想への正しい道標を可視化する(ギャップを埋めるための道のりを知る)
3,週間タスクリスト機能
→ 理想へ近づくための継続的タスク管理(ギャップを埋めるための努力を管理する)
4,タスクタイマー・作業集中音楽機能
→ 理想達成のためにタスクへのモチベーション・集中力を加速(その努力の集中力を上げる)
5,休憩通知・次回の楽しい予定リスト機能
→ 今この時の人生を楽しみ、良いバランスで自己成長する(モチベーションを保ち継続を助ける)

### 1-3, ユーザーターゲット

- 幸せに生きたい人
- 理想の自分になりたい人
- モチベーションを上げたい人
- 物事を継続したい人
- 自己研鑽に没頭したい人
- iPhone(Android)、iPad(その他タブレット)を使用している人
- 日本語話者、英語話者、フランス語話者

### 1-4 アプリの特徴

- iOS / Android のモバイルアプリ(将来的にタブレット最適化)
- シンプルで使いやすい
- モダンでスタイリッシュな UI
- UI/UX でモチベーションアップを狙う
- 各機能でユーザーの継続力・集中力を促進
- 日本語、英語、フランス語対応

### 2-2-1,サインアップページ(フロント)

- ユーザ名
- メールアドレス
- パスワード
- 支払い方法(必要に応じて別リンクへ遷移)

### 2-2-2,サインアップページ(バック データベース)

Supabase Auth で「id」サインアップ時の「ユーザ名」「メールアドレス」「パスワード」を保持。
Supabase DB における users テーブル内の「id」は Auth の id と一致、「ユーザ名」「メールアドレス」も Auth の各データと同期させる。(ユーザ名とメールアドレスを変更可能にするため)
課金状態は Supabase DB における subscriptions テーブルで管理。
こちらで有料機能を開放するかを判定。(課金状態=アクティブ && ユーザログイン済み)
二度目の初月無料防止策として、DB 内の user テーブルに is_canceled フラグを作成し、ユーザ退会後もユーザデータを保持、再サインアップ時には実質「再アクティブ化」として is_canceled を false に変更する。また、再アクティブ時に user テーブル内の had_account_before をチェックし、true なら初月無料対象外

### 2-2-3,サインアップページ(バック 決済ロジック)

ユーザの決済手段・情報は本 PJ システムでは一切扱わない。
ユーザーは Apple ID / Google アカウントの支払い情報を使い、カード変更・削除も App Store / Google Play の設定画面で行う。

**【決済ロジック】**
ユーザがアプリ内の該当ボタン押下時に RevenueCat SDK を使って App Store / Google Play の課金フロー遷移される。→ 購入が成功するとレシートが発行される →RevenueCat SDK がそのレシートを RevenueCat サーバーに送る。→ そのレシートをもとに「ユーザが何をいつまで持っているか」を RevenueCat が管理。→Supabase DB のユーザサブスクリプション状態が更新される。

つまり revenueCat 決済ステータス変更時に DB 側で subscriptions テーブルが作成・更新される。
subscriptions 内の user_id は Supabase の UID と紐づける。
各支払期日に Apple / Google が自動で課金、RevenueCat が成否を監視、結果ステータスが変更したタイミングで RevenueCat → Webhook → DB と伝達、subscriptions が更新される。(「Status をアクティブに」や「current_period_end(次回支払日)」など)
解約は「解約する」ボタン押下時に Apple ストア/Android ストアに遷移させる。
ストアで解約すると RevenueCat のサブスクもキャンセル状態に。
そのタイミングで Supabase DB 更新。(subscriptions.cancel_at_period_end = true など) 有効期限までは status="active"のままだが、期限を過ぎたタイミングで revenueCat が status="canceled"に更新、DB にも status="canceled"を反映。アプリ自体は status を見て有料機能をロックにする

### 2-2-4,サインアップページ(バック セキュリティ)

【悪意あるユーザが「課金中」と偽装するリクエストを送る可能性】
RevenueCat の Webhook 署名・シークレットキーを用いてリクエストの正当性を検証、Supabase Edge Functions で署名チェックを実装 → サーバー側(Supabase)で生のリクエストボディと環境変数に置いたシークレットキーを使って HMAC で署名を再計算 → 計算結果とヘッダー値が一致するかを比較 → 一致の場合は本物の RevenueCat で対応、不一致の場合は偽リクエストとして 401/403 で拒否

【別ユーザのトークンで課金情報にアクセスできてしまう可能性】
・常に「現在ログインしている Supabase Auth UID」と subscriptions.user_id を比較
・RLS（行レベルセキュリティ）で「user_id が current_user.id の行しか読めない」ようにする。
つまりユーザーのアプリ → anon / authenticated ロール → RLS 有効 → 自分の行しか触れない。
バックエンド（Webhook）→ service_role → 管理者として全行を更新できる。
auth.uid() や auth.role()を使用して本人だけアクセス可能ポリシーを作成

### 2-7,理想の自分ページ

ユーザが「なりたい姿」を複数作成し、複数データを箇条書きで表示。
ページ上部に「追加」「削除」ボタンを配置。
追加ボタンを押すとインプットモーダルが出現し、そこに本文を打ち込める。
空文字は制御し、1 文字以上入力するとボタン押下が可能になる。
作成されたデータはリストとして表示される、1 データ 1 行。
データは user_ideal として DB に挿入される。（構造は data-structure.md を参照）
各行カードはクリックすると本文を更新するためのインプットモーダル(「追加」と同じデザイン)が出現し、本文を更新することができる。
各行カードの右側にはコントロールボタンを配置し、そのコントロールボタンを長押し+ドラッグすることでリストの順番を変えることができる。
削除ボタンを押すと各行カードのコントロールボタンが削除ボタンに変更になり、ユーザが削除ボタンを押すと該当の行が削除される。（削除時はユーザに Confirm を求める）
削除作業中は「削除」ボタンの文言がわかりやすい文言（検討中）に変更され、押下すると元の行＋コントロールボタンの表示に戻る。

- なりたい姿作成機能
- なりたい姿リスト表示機能
- なりたい姿編集機能
- なりたい姿削除機能
- 表示されたリストをドラッグで位置変更する機能

### 2-8, 年間目標ページ

ユーザが「なりたい姿」をもとに年間目標を設定。
ユーザは 1 年分のみデータの CRUD 操作可能。
理想の自分ページと同様にタイトルカードには追加と削除のボタンを配置。
追加ボタンを押すとインプットモーダルが表示され、そこに「年間目標」を入力し送信する。
理想の自分と同様に年間目標リストはカードとして表示され、カードには「本文」「カラー」「編集ボタン・削除ボタン」が表示され、長押しタップ＋ドラッグでリストの順番を変更できる。
ここまでの仕様・デザインは理想の自分ページと同じ、ここからが理想の自分ページと異なる点。
紐づいた月間目標に積み上げられた作業時間をもとに各年間目標に費やした時間の割合を計算、ドーナツ型円グラフとしてタイトルカード内に表示させる。ドーナツ型円グラフの色はユーザが選んだカラーを使用。ドーナツ型円グラフの右側には「全てのタスクを合計した総作業時間」を表示。
そうすることで各年間目標を均等に達成できるようにユーザがバランスよく月間目標を整理できる。

- 年間目標作成機能
- 年間目標リスト表示機能
- 年間目標編集機能
- 年間目標削除機能
- 年間目標リストをドラッグで位置変更する機能
- 各年間目標をカテゴリーラベルとして各月の月間目標に付与する機能
- 各月の各月間目標の作業時間をもとに紐づいた 1 つの年間目標の作業時間を計算
- 各年間目標に積み上げられた作業時間の割合を計算し円グラフを作成、表示

### 2-9, 月間目標ページ

「年間目標」をもとにユーザが月間目標を設定。
【タイトルカード】
縦並べで１行目「タイトル」2 行目「追加ボタン、削除ボタン」3 行目「月指定ボタン」4 行目「達成度ゲージバー ＋ 月の総作業時間」
タイトル、追加ボタン、削除ボタンは年間目標ページと全く同じ仕様。追加カルーセルは「月間目標（本文）」「何月（ユーザが現在指定している月がデフォルト値として入力されている）」「紐付ける年間目標（プルダウン選択式）」「目標作業時間」を入力できる。（編集も同様）
プルダウン選択式で表示する各年間目標は UI が壊れない程度の文字数だけを表示しそれ以降は「...」で折りたたむ。
ユーザは 12 か月分、各月毎に月間目標を管理可能。「月指定ボタン」でユーザが選択した月の月間目標リストが表示され、そこで CRUD 操作も可能になる。
月指定ボタンはカルーセルタイプにして、最大 3 ヶ月分を画面上に表示できる使用にしたい。（それ以前と以降は横スクロールでスライドできる）
達成度ゲージバー(プログレスバー)はユーザが指定した各月間目標作業時間の合計と実際にユーザが作業した時間の合計をもとに算出、生成。
その下部に各月間目標作業時間の合計と総作業時間の数字を表示。
【各月間目標カード】
本文、目標時間と実際の作業時間から算出されたゲージバー（プログレスバー）、目標時間と作業時間の数値、編集・削除ボタンを表示。
１つ月の各月間目標は各週間タスクに紐づいている。
各週間タスクの作業時間に応じて紐づいた１つの月の各月間目標の作業時間が積み上げられる。
ここで積み上げられた月間作業時間は紐づいた年間目標に積み上げられる。

【↓ 一定期間後の実装 ↓】
ゲージバーが 100%の場合、表示の際に光沢アニメーションを付与する
達成度の計算は「タイマー終了時」などイベント発火時に行い、DB に保存した値をゲージバー(プログレスバー)で表示する。(不要な再レンダリングを防ぐため)

- 月間目標作成機能(達成目標時間数も指定)
- 月間目標リスト表示機能
- 月間目標編集機能
- 月間目標削除機能
- 月間目標リストをドラッグで位置変更する機能
- 各年間目標をカテゴリーラベルとして各月の各月間目標に付与する機能
- 各月の各月間目標の作業時間の合計が紐づいた年間目標に積み上げられる機能
- 各月の各月間目標リストを 1 カテゴリー(タスク A(〇月)など)とし、各週間タスクに紐づける機能
- 紐づけた週間タスクの作業時間を月間目標に積み上げる機能
- 積み上げられた作業時間と作業目標時間数で達成度を計測し、ゲージバー(プログレスバー)を生成して下部に表示する機能

### 2-10, 週間タスクページ

「月間目標」をもとにユーザが週間タスクを設定。
タイトルカードには「タイトル」「今週・来週・先週メモトグルボタン」「ゲージバー（月間目標ページと同じ仕様）」「追加・削除・来週メモ適用ボタン（来週目も適用ボタンは削除モードの時は非表示）」を設置
今週タスク、来週メモ、先週メモの３ページを用意(上部のトグルボタンで切り替え)
ユーザが主にタスク管理で使用するのは今週ページ。
来週メモは来週分の作業を洗い出すためのシンプルなメモ。
先週メモはユーザが先週のタスクを振り返るための履歴メモ。
ユーザが週終わりに「来週メモ適用ボタン」を押すことで「先週メモの削除 → 　今週作業リストを先週メモへ → 来週メモを今週タスクへ移行 → 来週メモをリセット」を行えるようにする（ポップアップメッセージでユーザに機能をしっかり説明した上で confirm をもらう）
各週間タスクに目標時間を設定。
各タスクは 1 つの月の 1 つの月間目標と紐づいている。(何月と紐づけるかも設定)
タスクタイマーで計測した作業時間を指定されたタスク作業時間(accumulated_time_week)に積み上げる。
積み上げられた作業時間とそのタスクの作業時間目標をもとに週間達成度を計測、ゲージバー(プログレスバー)にして下部に表示。（月間目標ページと同じ使用）
ここで該当のタスクに積み上げられた時間(accumulated_time_week)は紐づく月間目標の作業時間(accumulated_time_month)にも積み上げられる。
また、その月間ページに紐づいた年間目標の作業時間(accumulated_time_year)にも積み上げられる。
週間タスクが削除されても既に積み上げられた月間目標の作業時間(accumulated_time_month)と年間目標の作業時間(accumulated_time_year)には影響が出ない（既に積み上げられた作業時間は記録として残り続ける）
各タスクカードは月間目標と同じ仕様・デザイン。
今週分のみタスクカードの最下部にタイマーページへ遷移するボタンと手動作業時間積み上げボタンの二つを設置。
(ここで遷移元のタスクがタスクタイマーに紐づいて作業時間に応じて積み上げられる)
ここでタスク時間を計測する（関連する週間タスク・月間タスク・年間タスク全てに利用される）
※タスク作業時間の積み上げは「タイマー終了時」にイベントを発火させ、DB に保存した値をもとにゲージバー(プログレスバー)などを表示する。(不要な再レンダリングを防ぐ)
手動積み上げボタンを押すとモーダルが出現し、手動で時間数を入力でき、accumulated_time_week、紐づく月間目標の accumulated_time_month、紐づく年間目標の accumulated_time_year）が更新される。（アプリが使用できない場合に積み上げた作業時間をユーザが後日積み上げられるように）

- 週間タスク作成機能(目標時間数も指定)
- 週間タスクリスト表示機能
- 週間タスク編集機能
- 週間タスク削除機能
- 週間リストをドラッグで位置変更する機能
- 複数週間タスクと１つの月の１つの月間目標の紐づけ機能
- 各週間タスク下部に達成度を表すゲージバー(プログレスバー)表示機能
- タスクタイマーへ遷移するリンクボタン
- タスクタイマーの計測時間に応じてその週間タスクの作業時間が積み上げられる
- 積み上げられた作業時間の合計を計測する機能
- 作業時間と設定された目標時間を基に達成度を表す週間タスク用ゲージバー(プログレスバー)を作成、各タスクの下部に表示
- 積み上げられた作業時間をタスクと紐づく月間目標にも積み上げ、月間目標用ゲージバー(プログレスバー)にも適用。
- タスク時間手動積み上げ機能(アプリ未使用時の自己研鑽も記録に残せるように)

### 2-11-1 タスクタイマー機能(フロントエンド)

ユーザが各週間タスクの作業中に作業時間を計測するタイマー。
各週間タスクカード内の「作業タイマー」ボタンを押すとタスクタイマーページに遷移する。
その際にボタンを押したタスクカードの情報が紐付き、計測データはそこに反映される。
タスクタイマーページを開いた段階でユーザが通知設定を許可していなかった場合、「タイマー終了時に通知するため通知を許可して下さい」とポップアップメッセージを表示。

タスクタイマーページにタイトルカード、フッターを配置しない・
タイマーカードと操作カードのみ。
＜タイマーカード＞
タイマーカードには進捗リングと６つの操作ボタン、その下にスタートボタンを配置。
進捗リングは「ユーザが入力した作業時間」と「残り時間」をもとに生成、表示される。
進捗リングの中央には 1 行目に「残り時間/ユーザが入力した作業時間」2 行目に「終了予定時間」を表示。
その下に配置する 6 つのボタンは「+5m」「+10m」「+30m」「+1h」「+2h」「クリア」
各ボタンを押下すると「ユーザが入力した作業時間」がボタンに応じて計算される。
クリアボタンは「ユーザが入力した作業時間」を０にする。
ユーザが作業時間を確定させたら「スタートボタン」を押すことでカウントダウンがスタートする。
カウントダウン中はスタートボタンを非表示にする。
時間が 0 になった時アラームとバイブでユーザに知らせ、画面上には「作業終了」のポップアップメッセージを表示。

＜操作カード＞
操作カードには４つのボタンを配置。
１、「一旦停止/再生」ボタン。タイマーを一時停止、再度押すと再開できる。トグル形式で表示を「一旦停止」「再生」に切り替える。カウントダウンが始まる前は disable とする。
２、「作業完了」ボタン。このボタンを押すと confirm ポップアップが出現し、ユーザが OK とすると現在の作業時間を記録し作業タイマーが終了する。（週間タスクページへ遷移する）その際に「経過時間を記録しました」トーストを表示する。
３、「音楽再生/停止」ボタン。音楽音楽を一時停止、再度押すと再開できる。トグル形式で表示を「音楽停止」「音楽再生」に切り替える。タスク集中音楽ページで選択されたデフォルト音楽が再生される。
４、「音楽選択」ボタン。ボタンを押すとモーダルページが出現し、ユーザがすでにダウンロードしている５つの音楽が選択肢として表示される。そこからユーザは音楽を選択でき、選択と同時に選択された音楽が再生される。

### 2-11-2 タスクタイマー機能(バックエンド)

作業タイマーによって記録された作業時間は作業タイマー開始時に紐づけられた週間タスク(作業タイマーへ遷移した時の遷移元)の accumulated_time_week に積み上げられる。
また、同様に該当週間タスクに紐づく月間目標(monthly_goals.ccumulated_time_month)、年間目標(yearly_goals.accumulated_time_year)にも蓄積される。

作業タイマーはユーザがアプリを閉じてもスマートフォンのバックグランドで継続して計測できる。
カウントダウンはタイマーではなく時刻差分で計測することでそれを実現させる。
保存する状態は以下の６つ。

- status: "idle" | "running" | "paused" | "finished"
- durationMs: 設定時間（例 2h30m）
- startedAt: 開始した実時刻（epoch ms）
- pausedAt（一時停止中なら）
- accumulatedMs（一時停止までの累計経過）
- scheduledNotificationId（終了通知の ID）
  残り時間は以下のように計算。
  running：remaining = durationMs - (now - startedAt + accumulatedMs)
  paused：remaining = durationMs - accumulatedMs

アプリを閉じてもカウントが 0 になった時点で通知を出す。
開始時に「終了時刻のローカル通知」を予約(expo-notifications)
作業タイマー開始時に endAt = now + remaining として endAt を算出し、expo-notifications の scheduleNotificationAsync で endAt に通知（通知音あり）
作業タイマーを「一時停止、作業完了、作業中断」した際は予約通知 cancelScheduledNotificationAsync でキャンセルする。
一時停止状態から再度タイマーを再開した時は新しい endAt を算出し再度通知を予約。
また、expo-haptics で終了時のバイブレーションも実現。

作業タイマー中のタスク集中音楽について。
音楽プレイヤーは App 全体で一つの仕様にする(Provider)
作業タイマーの画面ではその状態を操作するだけ。
react-native-track-player(開発ビルド)を使用して音楽の再生・停止を管理する。
repeat track で 2,3 分の曲を無限ループさせる。
タスク集中音楽もバックグラウンドで再生可能にする。（スワイプなどでアプリが強制的に終了した場合を除く）
Standalone/EAS ビルド＋ UIBackgroundModes: ["audio"] で iOS バックグラウンド再生を実現。
setAudioModeAsync({ shouldPlayInBackground: true, playsInSilentMode: true, ... }) でバックグラウンド再生・割り込み挙動を整える。

　 ＜以下は今後検討！　以下軽微なエラーはノイズとして除去する＞

- Network request failed
  一時的な通信断や電波不安定で発生しやすい汎用ネットワーク失敗。再試行で回復することが多い。
- TypeError: Network request failed
  上と同系統の通信失敗。fetch実装や環境差でTypeErrorとして出るパターン。
- Failed to fetch
  fetchがサーバー到達前に失敗したときの代表的エラー。瞬断・DNS・オフラインで出やすい。
- Load failed（通信瞬断起因のみ）
  データ取得中に回線が落ちたケース。恒常的なロジック不具合でない前提ならノイズになりやすい。
- Request timed out
  サーバー応答待ちがタイムアウトした状態。混雑時や一時的遅延で発生し、再試行で成功しやすい。
- TimeoutError
  タイムアウト系の例外名。上記と同じく一過性の可能性が高い。
- ERR_NETWORK（再試行で回復する一時ネットワーク）
  通信レイヤーの一時失敗。恒常障害と切り分けが必要で、単発はノイズになりやすい。
- No internet connection（Offline検知済み画面での想定内）
  オフライン時に想定どおり出るエラー。Offline UIでハンドリング済みなら送信不要。
- 429（一時的レート制限、リトライ前提のもの）
  リクエスト過多による制限。短時間で回復することが多く、単発通知はノイズになりやすい。
